# Inside Client — бэкенд личного кабинета

К сайту добавлен полноценный backend на Node.js (без внешних зависимостей —
используется встроенный в Node 22 `node:sqlite` и глобальный `fetch`),
который отвечает за регистрацию, авторизацию, данные личного кабинета и
привязку Telegram через бота.

## Запуск сайта

```bash
node server/server.js
# или
npm start
```

Требуется **Node.js 22.5+** (нужен модуль `node:sqlite`). Сервер поднимется на
`http://localhost:3000` и сам раздаёт весь сайт (html/css/js), плюс API.
Порт можно поменять переменной окружения `PORT`.

При первом запуске автоматически создаётся файл базы данных
`data/inside-client.sqlite` со всеми таблицами и несколькими демо-ключами
активации:

```
DEMO-1111-2222-3333
DEMO-4444-5555-6666
DEMO-7777-8888-9999
```

(каждый выдаёт доступ к «Клиент 1.16.5», активировать можно только один раз).

## Запуск Telegram-бота

Бот — отдельный процесс, работает через long polling (сам стучится к
Telegram), поэтому **не нужен ни домен, ни HTTPS, ни открытые порты** —
подходит для локального запуска рядом с сайтом.

```bash
TELEGRAM_BOT_TOKEN=<токен из @BotFather> node server/bot.js
```

Бот использует ту же SQLite-базу, что и сайт (`server/db.js`), и пишет туда
напрямую — отдельного внутреннего API между сайтом и ботом не требуется.

**Важно про токен:**
- Никогда не коммитьте токен в файлы проекта — передавайте только через
  переменную окружения `TELEGRAM_BOT_TOKEN`.
- Если токен когда-либо «засветился» (например, был вставлен в чат, скрипт
  или публичный репозиторий), стоит перевыпустить его через `@BotFather`
  командой `/revoke`.

Сайту нужно знать **username** бота (это публичная информация, не секрет),
чтобы строить диплинк вида `t.me/<бот>?start=<код>`. По умолчанию используется
`InsideClientBot`; если username бота другой или изменится, задайте его через
переменную окружения при запуске сайта:

```bash
TELEGRAM_BOT_USERNAME=InsideClientBot node server/server.js
```

## Логика личного кабинета

- **UID** — обычный автоинкремент в таблице `users`. Первый
  зарегистрированный пользователь получает UID `1`, следующий — `2`, и т.д.
- **Логин** — вводится при регистрации, 3–20 символов
  (латиница/цифры/`_`), должен быть уникален (без учёта регистра).
  Вход — только по логину. Email в проекте не используется.
- **Пароль** — хранится не в открытом виде: `scrypt` + случайная соль
  (модуль `crypto`, без сторонних библиотек).
- **Группа** — «Пользователь», если у аккаунта есть хотя бы одна покупка
  клиента (через магазин или активацию ключа); иначе «Нету».
- **HWID** — `NULL`, пока не привязан лаунчером (в кабинете тогда пишет
  «Нету»). Кнопка «Сбросить» отправляет на страницу покупки (сброс HWID
  оформляется как отдельная услуга).
- **Телеграм** — обязателен перед покупкой (1 Telegram-аккаунт = 1 аккаунт
  на сайте). Привязка происходит через бота:
  1. Пользователь жмёт «Привязать» в личном кабинете →
     `POST /api/telegram/start-link` создаёт одноразовый код (живёт 10 минут)
     и возвращает диплинк `t.me/<бот>?start=<код>`.
  2. Ссылка открывается в Telegram, бот получает `/start <код>`, проверяет
     его в таблице `telegram_link_codes` и записывает `telegram_chat_id` +
     `telegram_username` в `users`.
  3. Личный кабинет параллельно опрашивает `/api/me` каждые несколько секунд
     и как только видит `telegramLinked: true` — сам обновляет интерфейс.
  Уникальность обеспечивается на уровне `chat_id` (а не `username` — в
  Telegram username необязателен, а chat_id есть всегда и не меняется),
  плюс бот и сервер сами проверяют, что этот Telegram ещё не привязан к
  другому аккаунту.
- **Дата регистрации / последний вход** — простановляются сервером
  автоматически.
- **Купленные товары / активация ключа** — покупка тарифа на `buy.html`
  или ввод ключа в личном кабинете добавляет запись в таблицу `purchases`
  и сразу переводит аккаунт в группу «Пользователь». Покупка на `buy.html`
  сейчас тоже заглушка на клиенте (страница оплаты ещё не готова), но
  сервер (`/api/purchases/buy`) уже требует привязанный Telegram и вернёт
  ошибку 403, если его нет.

## Схема БД (SQLite)

```
users(id, login, password_hash, hwid,
      telegram_chat_id UNIQUE, telegram_username, created_at, last_login)
sessions(token, user_id, created_at, expires_at)
telegram_link_codes(code, user_id, created_at, expires_at, used)
purchases(id, user_id, product, source, purchased_at)
activation_keys(activation_key, product, used, used_by, used_at)
```

## API

| Метод | Путь                       | Описание                                   |
|-------|----------------------------|---------------------------------------------|
| POST  | `/api/register`            | Регистрация (`login`, `password`)          |
| POST  | `/api/login`               | Вход (`login`, `password`, `remember`)     |
| POST  | `/api/logout`              | Выход                                       |
| GET   | `/api/me`                  | Данные текущего аккаунта                    |
| POST  | `/api/hwid/reset`          | Сброс HWID                                  |
| POST  | `/api/telegram/start-link` | Сгенерировать код + диплинк на бота, 409 если Telegram уже привязан |
| POST  | `/api/telegram/unlink`     | Отвязать Telegram                           |
| POST  | `/api/password/change`     | Смена пароля (`oldPassword`, `newPassword`) |
| POST  | `/api/purchases/buy`       | «Покупка» тарифа с `buy.html` (`plan`), 403 если Telegram не привязан |
| POST  | `/api/key/activate`        | Активация ключа (`key`)                     |

### Привязка устройства (клиент)

Клиент — это отдельное приложение (Fabric-клиент), не браузер, поэтому у него
нет cookie-сессии. Первый запуск привязывает HWID к аккаунту напрямую по
логину/паролю, дальше клиент работает только по HWID:

| Метод | Путь                 | Описание                                                        |
|-------|----------------------|-------------------------------------------------------------------|
| POST  | `/api/client/bind`   | Первый запуск: `login`, `password`, `hwid`, `ip?` → привязывает HWID к аккаунту (или подтверждает, если это тот же HWID) |
| POST  | `/api/verify`        | Разовая проверка лицензии по `hwid` (+`ip`)                     |
| GET   | `/api/status?hwid=`  | Heartbeat, дёргается клиентом каждые ~2 мин, пока он запущен     |

`/api/client/bind` отказывает, если: неверный логин/пароль, аккаунт забанен,
нет активной подписки, или HWID аккаунта уже занят другим устройством (в
этом случае — сброс HWID в личном кабинете или у админа). Один HWID не может
быть привязан к двум аккаунтам одновременно — это гарантирует частичный
`UNIQUE`-индекс в БД (`idx_users_hwid_unique`), а не только проверка в коде.
Пароль передаётся один раз и клиентом не сохраняется — после успешной
привязки клиент хранит только HWID (он и так детерминированно вычисляется
из железа при каждом запуске) и дальше пользуется `/api/verify`/`/api/status`.

### Облачные конфиги

Именованные пресеты настроек клиента, привязанные к аккаунту. Личный кабинет
управляет ими по сессии, а сам клиент читает их напрямую по HWID — так же,
как ходит на `/api/verify`, без логина/cookie.

**Личный кабинет (сессия, `ic_sid`):**

| Метод | Путь                  | Описание                                        |
|-------|-----------------------|--------------------------------------------------|
| GET   | `/api/configs`         | Список пресетов (без содержимого)               |
| GET   | `/api/configs/get`     | Один пресет с содержимым (`?id=`)               |
| POST  | `/api/configs/create`  | Создать пресет (`name`, `content`)              |
| POST  | `/api/configs/update`  | Переименовать/изменить (`id`, `name?`, `content?`) |
| POST  | `/api/configs/delete`  | Удалить (`id`)                                   |

Лимиты: до 20 пресетов на аккаунт, до 256 КБ на пресет, имя — 1–40 символов,
уникально в рамках аккаунта (без учёта регистра).

**Клиент (HWID, отдельный модуль `server/configs-client.js`):**

| Метод | Путь                        | Описание                                  |
|-------|-----------------------------|--------------------------------------------|
| POST  | `/api/client/configs/list`  | Список пресетов по `hwid`                  |
| POST  | `/api/client/configs/get`   | Содержимое пресета по `hwid` + `name`      |

Доступ даётся на тех же условиях, что и сама лицензия клиента (см. `verify.js`):
HWID привязан к аккаунту, аккаунт не забанен, подписка активна. Отдельный
CORS + rate-limit, как у `/api/verify`, — маршрут не проходит через
`API_ROUTES` и не требует cookie.

Авторизация — через httpOnly cookie `ic_sid` (создаётся при входе/регистрации).

## Что стоит доделать для продакшена

- Реальная оплата вместо мгновенного зачисления покупки.
- HTTPS + флаг `Secure` для cookie, rate-limiting на `/api/login`,
  `/api/register` и `/api/telegram/start-link`.
- Бот сейчас держит процесс живым простым `for(;;)` циклом с обработкой
  ошибок и повтором через 5 секунд — для продакшена стоит завернуть его в
  systemd/pm2 (или аналог), чтобы он поднимался сам при падении сервера.
